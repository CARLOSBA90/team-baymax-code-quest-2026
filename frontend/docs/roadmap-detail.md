**Lesson checklist (fase 7/7, roadmap-detail-lessons).** An item with `tracking.type === "LESSONS"` and a real `syllabus` (`isLessonChecklistItem(item)` in `lib/roadmap-detail.ts`: `LESSONS` type + `syllabus !== null` + `totalLessons > 0`) renders `LessonChecklist` in `RoadmapItem` instead of `trackingMessage` — never both, and never alongside `CompleteButton` (`showCompleteButton = !isCompleted && canTrack(item.tracking)` is unchanged, and `canTrack` still excludes `LESSONS`; the item's "actions" area therefore only ever has the external course link there). Items with `syllabus: null` (`disabledReason: "SYLLABUS_MISSING"`, or any other tracking type) keep the existing generic `getTrackingUnavailableMessage` copy with no disclosure — never an empty checklist. Unlike `CompleteButton`, the checklist stays visible and interactive even when the item's `state` is `"completed"`: lessons are reversible (unchecking one drops `item.progress` below 100 and the item reverts to `in_progress`/`pending`), so `isLessonChecklistItem` does not depend on `state`. New grid area `lessons` in `RoadmapItem`'s card, full width, below `actions` in both breakpoints (`'thumb_body' 'actions_actions' 'lessons_lessons'` base, `'thumb_body' 'thumb_actions' 'lessons_lessons'` from `sm:` — no `grid-template-rows` added for it, so it never touches the existing `thumb`/`body`/`actions` classes).

`LessonChecklist { item: Pick<RoadmapItem, "roadmapItemId"|"name"|"syllabus">, headingId, locked, pendingKey, onToggle(lessonId, completed) }` (`components/roadmap-detail/LessonChecklist.tsx`) is the disclosure: a `button` (`aria-expanded`, `aria-controls` → the `<ul>`'s id from `getLessonListId(headingId, item.roadmapItemId)` = `` `${headingId}lessons-${roadmapItemId}` `` — note this concatenates directly onto the item's h3 id, e.g. `"tl-step-item-3lessons-item-3"`; valid HTML/ARIA but not pretty, a known cosmetic gotcha from the apply phase) with visible label "Temario · {getLessonsProgressLabel(completedLessons, totalLessons)}" (e.g. "Temario · 2 de 12 lecciones", singular "1 de 1 lección") and a `ChevronIcon` (`RoadmapDetailIcons.tsx`, rotates 180° when expanded). `expanded` is local `useState(false)`, **uncontrolled by the parent** and never reset by the pessimistic refetch after toggling a lesson (same `LessonChecklist` instance, same parent `<li key={item.roadmapItemId}>`) — so the disclosure stays open across consecutive toggles. The `<ul>` is always mounted (`hidden` when collapsed, never unmounted) grouped by `syllabus.sections`: one `<li>` per section with a visible (non-decorative) heading paragraph (`section.title`) plus a nested `<ul>` of `LessonRow`. `pendingKey` (`` `${roadmapItemId}:${lessonId}` `` of the lesson with a mutation in flight, or `null`) is threaded down as-is from `RoadmapDetailView` through `RoadmapItem`'s `lessonTracking: { locked, pendingKey }` prop — no intermediate component resolves it, each `LessonRow`'s `busy` is computed inline in `LessonChecklist`'s `.map` as `pendingKey === \`${item.roadmapItemId}:${lesson.lessonId}\``.

`LessonRow { lesson: SyllabusLesson, itemName, checked, disabled, busy, onToggle }` (`components/roadmap-detail/LessonRow.tsx`) is one `<li>` with a native checkbox: `checked = getLessonState(lesson) === "completed"`, `aria-label="{lesson.title}, {itemName}"` (disambiguates lessons with similar titles across courses — the visible label is just the lesson title). While `busy` (this lesson's own mutation in flight) the checkbox is **never** natively `disabled` — only `aria-busy="true"` — and `onChange` is a no-op guard against reentrancy, so the checkbox the user just toggled keeps focus and its tab stop without needing `useFocusRequest` to give it back afterwards (unlike the pause banner button, which *is* natively disabled and does need `requestFocus`). Every other checkbox (same item or other items) gets `disabled = locked && !busy` as a native attribute — losing their focus is acceptable since they aren't the control the user interacted with. `locked` comes from `RoadmapDetailView`'s `lessonsLocked = trackLocked || isPaused`, so **a paused roadmap disables every checkbox** just like it disables every `CompleteButton`: the backend rejects any report with 409 `ROADMAP_PAUSED`, so an enabled checkbox there could only produce an error notice. The pause is explained by the visible `PausedBanner`, not by `aria-describedby` on each checkbox (the `CompleteButton` pattern does not scale to a syllabus with hundreds of lessons).

**Wiring in `RoadmapDetailView`** (D1-D6 of the design): the mutation variable of `useTrackProgress`'s `trackMutation` is now a discriminated `TrackProgressVariables = { kind: "item", roadmapItemId } | { kind: "lesson", roadmapItemId, lessonId, completed }`, same `mutationKey`, same pessimistic cycle (exact detail refetch, list invalidation without awaiting, cache patch on non-404 refetch failure, never `roadmapsKeys.all`) — parametrized, not duplicated. `progress.service.ts` gained a private `postTrackProgress` helper shared by `trackItemCompletion` (unchanged body/behavior: still `{roadmap_item_id, completed: true}`) and the new `trackLessonCompletion(roadmapItemId, lessonId, completed)` (`{roadmap_item_id, lesson_id, completed}` — a **separate** `TrackLessonCompletionBody` interface in `types/progress.ts`, not optional fields on `TrackItemCompletionBody`, so the compiler — not just runtime 422s — prevents sending `lesson_id` for a COMPLETION/READING item). `roadmaps-cache.ts::applyTrackProgressResult` takes `variables: TrackProgressVariables` instead of a bare `roadmapItemId`; for `kind: "lesson"` a private `patchSyllabusLesson` immutably marks the lesson `completed` inside `syllabus.sections[].lessons[]` and recalculates `completedLessons` by counting.

`trackLocked = trackMutation.isPending || pauseLocked` (replacing the narrower `pauseLocked` that used to gate only `completeDisabled`) now also gates `CompleteButton` everywhere (`RoadmapTimeline`/`NextStepCard`'s `completeDisabled`) while **any** lesson toggle or item completion is in flight for **any** item — deliberately broad locking (no fine-grained per-lesson concurrency), the same precedent already used for pause/resume. `pendingLessonKey` is derived from `trackMutation.variables` when `isPending && kind === "lesson"`. `handleLessonToggle(item, lesson)` in `RoadmapDetailView.tsx` calls `clearFeedback()` then `trackMutation.mutate({ kind: "lesson", roadmapItemId, lessonId, completed: !lesson.completed }, { onSuccess, onError })` — **no confirmation dialog** (unlike completing an item, this is reversible) and **focus never moves** (the checkbox never lost it, per `LessonRow`'s `aria-busy` approach). `onSuccess` announces via `getLessonToggledAnnouncement({ lessonTitle, marked, itemName, itemProgress, completedLessons, totalLessons, roadmapCompleted })` (`lib/roadmap-detail.ts`) into the same always-mounted `roadmap-detail-announcer` live region used by item completion: "{lessonTitle} marcada como completada. {getLessonsProgressLabel(...)} en {itemName}." with " Completaste la ruta." appended only when `marked && roadmapCompleted` (never on unmark). `onError` sets the compositor's top `Notice` (never a dialog) via `getLessonTrackErrorMessage(error)` (`lib/roadmap-progress-errors.ts`), variant `"info"` when `shouldRefreshAfterTrackError(error)` else `"error"`.

**Errors when toggling a lesson** (`getLessonTrackErrorMessage`, checked in this order, never the backend's raw `message`): no response (network) → `TRACK_NETWORK_MESSAGE`; 409 `ROADMAP_PAUSED` → reused `ROADMAP_PAUSED_TRACK_MESSAGE`; 422 `TRACKING_REPORT_MISMATCH` → reused `TRACKING_MISMATCH_TRACK_MESSAGE`; 422 `SYLLABUS_MISSING` (new predicate `isSyllabusMissingError`) → new `SYLLABUS_MISSING_TRACK_MESSAGE` ("Ya no podemos registrar el avance de este curso. Hemos actualizado la ruta.") — the checklist itself can disappear after the ensuing refetch, since the item no longer qualifies for `isLessonChecklistItem`; 422 `LESSON_NOT_IN_ITEM` (new predicate `isLessonNotInItemError`) → new `LESSON_NOT_IN_ITEM_TRACK_MESSAGE` ("Esta lección ya no está disponible. Hemos actualizado la ruta.") — a stale syllabus on the client referencing a `lessonId` the course no longer has; 404 → reused `ROADMAP_ITEM_NOT_FOUND_MESSAGE`; anything else → generic `TRACK_GENERIC_MESSAGE`. `shouldRefreshAfterTrackError` was extended to return `true` for the two new codes too (it already covered paused/mismatch/not-found), so a detail refetch follows every one of those five error cases exactly like it already does for item completion; only network/5xx/other leave the cache untouched.

`next_step.lesson` (`RoadmapNextStep.lesson: SyllabusNextLesson | null`, same shape as `syllabus.nextLesson`) is mapped end to end in `roadmaps.service.ts::toRoadmapDetail` but **`NextStepCard` does not read it** — deliberately deferred to a future phase; "Continúa aquí" still shows only the course name, not the specific next lesson. `position_seconds` on `SyllabusLesson`/`SyllabusNextLesson` is likewise mapped but unused — no scrubbing/resume UI this phase, only mark/unmark complete.
